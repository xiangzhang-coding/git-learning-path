# Работа на ветке

## Цели урока

- Коммитить на ветке и понимать, что коммит попадает только в текущую ветку
- Понимать расхождение: коммит-граф расходится от общего предка
- Наблюдать структуру веток по коммит-графу в зоне практики

## Коммиты попадают только в текущую ветку

После создания ветки **коммиты попадают только в текущую ветку**. Допустим, `main` находится на commit A, и вы делаете:

```bash
git switch -c feature
# меняете код
git commit -m "feat: login page"
```

Этот коммит продвигает только `feature`; `main` остаётся на A. Вернувшись на main, вы не увидите ни этого коммита, ни того файла — рабочий каталог восстановится до снимка A.

**В этом и состоит основное назначение веток**: на feature можно свободно экспериментировать, а main остаётся стабильным.

## Расхождение и коммит-граф

Когда main и feature коммитят по отдельности, история расходится от общего предка:

```
o  A (общая точка старта main и feature)
|\
o |  B (новый коммит main)
| o  C (новый коммит feature)
```

Такая структура называется **коммит-графом (commit graph)**; технически это DAG (направленный ациклический граф) — у каждого коммита не больше двух родителей, циклов нет. Коммит-граф в нижней части зоны практики рисует его в реальном времени: имя ветки стоит прямо на её кончике.

## git log: изучаем историю

```bash
git log --oneline
```

`git log` показывает историю только **текущей ветки**. Переключитесь на feature — увидите её линию; вернитесь на main — увидите линию main. Чтобы видеть коммиты всех веток сразу, удобнее всего коммит-граф в зоне практики.
