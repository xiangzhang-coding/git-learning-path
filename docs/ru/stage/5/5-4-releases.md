# Releases и выпуск версий

## Цели урока

- Понять правила семантического версионирования
- Создать tag и отправить его на GitHub
- Создать Release с описанием и файлами

## Семантическое версионирование

Номер версии MAJOR.MINOR.PATCH (например, 2.4.1):

| Разряд | Когда повышается |
| --- | --- |
| MAJOR — мажорный | Ломающие изменения, несовместимо со старыми версиями |
| MINOR — минорный | Новая функциональность, обратная совместимость |
| PATCH — патч | Исправления багов, без новой функциональности |

Правило простое: повышение мажорной версии объясняет, почему программа внезапно сломалась, а повышение патча означает «обновляться безопасно».

## Создание tag и push

Перед выпуском создаём tag локально (это было в главе 4):

```bash
git tag -a v1.0.0 -m "v1.0.0: first release"
git push origin v1.0.0
```

Обратите внимание: по умолчанию `git push` не отправляет теги — нужен явный `git push origin <tag>` (или сразу все: `git push --tags`).

## Создание Release

На GitHub: страница репозитория → Releases → Draft a new release:

1. Выбрать (или создать) tag, например v1.0.0
2. Написать заголовок и описание выпуска (release notes)
3. Можно приложить бинарные файлы (установщики, сборки)
4. Нажать Publish release

Release — это «tag с описанием»: здесь пользователи скачивают версии и смотрят изменения, не заглядывая в git log.

## Как писать release notes

Хорошее описание группируется по читателям:

- **Новое** (Features): новые функции, можно ссылаться на PR
- **Исправления** (Bug fixes): что починили, можно ссылаться на issue
- **Ломающие изменения** (Breaking changes): на что обратить внимание при обновлении

## Практика на реальном GitHub

- Создайте в своём проекте tag v0.1.0 и отправьте его
- Оформите первый Release с описанием из трёх разделов
- Опубликуйте патч-версию и посмотрите на список Releases
