# Зачем нужен контроль версий?

## Цели урока

- Понять, какие проблемы решает система контроля версий (VCS)
- Сравнить централизованный и распределённый контроль версий
- Узнать, к какому типу относится Git

## Боль без контроля версий

Представьте проект в работе: на середине вы понимаете, что подход не работает, и хотите вернуться к состоянию вчерашнего дня — где этот файл? Может, в `final_v2_бэкап`, а может, уже перезаписан. Совместная работа ещё хуже: два человека правят один файл, побеждает тот, кто сохранил последним, а изменения другого бесследно исчезают.

Эти три проблемы — **записывать, откатывать, сотрудничать** — и есть то, что решает Git.

## Что такое контроль версий

Система контроля версий (VCS) записывает каждое изменение и хранит полный **снимок** проекта в каждый момент времени, что позволяет:

- просматривать любую историческую версию
- сравнивать различия между любыми двумя состояниями
- возвращаться к любому прошлому состоянию

Это не инструмент резервного копирования: резервная копия хранит только последнюю версию, а VCS сохраняет всю историю, и каждая версия восстанавливаема.

## Централизованный против распределённого

- **Централизованный (напр. SVN)**: один центральный репозиторий; все делают из него checkout, и каждый коммит должен пройти через сеть. Сервер упал — коммитить нельзя никому.
- **Распределённый (напр. Git)**: каждый клон — полная копия центрального репозитория. Коммиты происходят локально, даже офлайн; позже вы отправляете их другим.

Поскольку каждый коммит Git хранит полный снимок, а не diff, вся история полностью восстанавливается из любого клона — именно это и делает «распределённость» возможной.

## Анимация: перемотка линии времени

Двигайте ползунок или нажимайте на точки: содержимое файлов меняется с каждой версией — «вернуться в прошлое» и есть то, что даёт контроль версий.
