# git worktree: несколько рабочих деревьев

## Цели урока

- Создавать дополнительные рабочие каталоги для одного репозитория командой git worktree
- Понимать, что все worktree разделяют объекты и refs, но хранят отдельные HEAD
- Перечислять и удалять worktree; знать, зачем их используют агенты

## Один репозиторий: одно рабочее дерево

По умолчанию один репозиторий означает один рабочий каталог. Вы извлекаете одну ветку, редактируете файлы, коммитите — а когда нужна другая ветка, выполняете `git switch`, и весь каталог меняет содержимое.

У такого переключения есть цена: незавершённую работу на текущей ветке нужно сначала закоммитить или спрятать через stash, а поскольку обе ветки делят один каталог, две ветки одновременно увидеть нельзя.

`git worktree` ломает это правило «один к одному». **Worktree** — это дополнительный рабочий каталог, прикреплённый к тому же репозиторию:

```
your project/            <- основное рабочее дерево (исходное)
├── .git/                <- общее: объекты, refs, config
├── src/  (ветка main)
└── ...
your project-hotfix/     <- второй worktree (добавлен через git worktree add)
└── src/  (ветка hotfix)   <- другая ветка, другой каталог
```

Все worktree **разделяют общую базу объектов и refs** — коммит, сделанный в одном worktree, виден во всех остальных — но у каждого worktree **свои HEAD и index**, поэтому каждый может сидеть на своей ветке, не мешая остальным.

## git worktree add: второе рабочее дерево

```bash
git worktree add <path> <branch>
```

Создаёт новый рабочий каталог в `<path>` и извлекает там ветку `<branch>`. Несколько частых форм:

```bash
git worktree add ../hotfix hotfix         # check out existing branch hotfix
git worktree add -b fix-login ../login    # create branch fix-login and check it out
git worktree add --detach ../explore v1.2 # detached HEAD at a tag
```

Полезные детали:

- Если ветка уже существует, путь должен быть пустым — git не перезапишет каталог, в котором есть файлы.
- Ветка может быть извлечена **только в одном worktree**. Попытка извлечь ту же ветку во второй worktree завершится ошибкой `fatal: '<branch>' is already checked out at ...`.
- При `git clone` получается полноценный отдельный репозиторий; worktree — **не** клон: у него нет собственного каталога `.git`, он указывает на `.git` родительского репозитория.

## git worktree list: список worktree

```bash
git worktree list
```

Показывает каждый worktree, прикреплённый к репозиторию, — путь, извлечённую ветку и какой из них основной:

```
/path/your-project        abc1234 [main]
/path/your-project-hotfix def5678 [hotfix]
```

Основной worktree — это каталог, в котором репозиторий был изначально клонирован или создан; его удалить нельзя.

## git worktree remove: удаление

```bash
git worktree remove <path>
```

Удаляет рабочий каталог и отвязывает worktree. Два предохранителя:

- В каталоге не должно быть untracked- или изменённых файлов — иначе git откажется и предложит закоммитить, спрятать через stash или использовать `-f`.
- `git worktree remove -f <path>` удаляет и при наличии изменений, отбрасывая их.

Удалённый worktree оставляет ветку (и её коммиты) в покое: указатель ветки по-прежнему существует в репозитории и готов к извлечению в основном worktree позже.

## Почему агенты любят worktree

AI-агенты для программирования (Claude Code, Cursor и подобные) часто работают сразу над несколькими задачами. Без worktree агенту при переключении задач приходится коммитить или прятать в stash, переключать ветки, а затем распутывать изменения — и одна ошибка может смешать правки одной задачи в коммит другой ветки.

С `git worktree add` каждая задача получает **свой каталог и свою ветку** в полной изоляции:

- Агент задачи A редактирует `../task-a` в ветке `feature/login`
- Агент задачи B редактирует `../task-b` в ветке `fix/typo`
- Оба коммита попадают в один репозиторий; ни один из них не может тронуть файлы другого

Когда вы проверяете результат, каждая ветка — чистый самостоятельный блок, и при этом остаётся одна общая история для push. Именно эта изоляция сделала рабочие процессы на основе worktree нормой для разработки с агентами.

## Когда использовать worktree

Используйте их, когда:

- Нужно работать с двумя ветками одновременно (hotfix, пока продолжается работа над фичей)
- Вы запускаете долгие тесты или dev-сервер в одном worktree и продолжаете редактировать в другом
- Агенты или командные инструменты выполняют параллельные изолированные задачи

Пропустите их, когда в норме одна задача за раз — лишние каталоги добавляют учёт без пользы.
